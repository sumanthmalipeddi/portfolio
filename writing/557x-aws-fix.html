The 60-second stall: a 557× AWS fix

EC2 · boto3 · DNS · IPv6

The symptom

Every AWS SDK call on a production box stalled almost exactly 60 seconds. An 889 KB S3 upload took 481 seconds. sts get-caller-identity — a call that returns a few hundred bytes — took 61. The box had been misdiagnosed twice before I got to it, because curl against the same endpoints looked completely healthy.

The diagnosis

The number was too consistent to be bandwidth. Three timed runs repeated to within 45 milliseconds — real network degradation doesn't do that. A delay that reproducible is a fixed timeout somewhere, and the job was to find which one.

The instance advertised an IPv6 default route with dead egress. Python resolves AAAA records first, attempts IPv6, and waits out the full connection timeout before falling back to IPv4. curl implements happy-eyeballs — it races both address families and takes whichever connects — which is exactly why it looked fine the whole time, and exactly why the box had been misdiagnosed twice.

The fix

One line in /etc/gai.conf to prefer IPv4 address resolution. A colleague had proposed a VPC-endpoint change as the fix; I tested it and disproved it by measurement before it shipped — the endpoint wasn't the problem, the resolver order was.

  • 481s → 0.86s S3 upload (889 KB) — 557×
  • 61s → 0.74s sts get-caller-identity — 82×

The lesson

A repeatable delay is a timeout, not a slow network. And two tools disagreeing about the same endpoint isn't noise — it's the diagnosis: find what one does that the other doesn't, and the bug is usually living in the difference.
